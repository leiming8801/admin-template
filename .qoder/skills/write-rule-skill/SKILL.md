# 如何编写 Rule

> **Rule 的本质**：明确告诉 AI 做什么或不做什么的约束。AI 只需遵守，无需判断"视情况而定"。

---

## 1. 三原则

| 原则             | 说明                                             | 违背示例                          | 正确做法                       |
| :--------------- | :----------------------------------------------- | :-------------------------------- | :----------------------------- |
| 简单明确，能少不多 | 每条一句话说清，不写流程图、大段示例、话术模板 | 100 行描述 + 流程图 + 话术模板    | 只保留约束本身，无冗余段落     |
| 同主题合并       | 同一主题域合并成一个文件                         | 操作安全一个文件、审批流程又一个  | 审批触发条件并入操作安全规则   |
| 主题不同才新建   | 确认与现有规则重叠 < 50% 才新建                  | 为"依赖升级"单独建一个 rule       | 并入复用优先 / 操作安全        |

---

## 2. 什么时候该写 Rule

必须全部满足：

1. **约束性**：是禁止 / 强制，不是"怎么解决"
2. **跨项目或稳定成立**：换产品仍成立，或至少长期不变
3. **结论唯一**：没有"视情况而定"的分支

不该写成 Rule 的内容：

| 内容类型                     | 正确归宿                                     |
| :--------------------------- | :------------------------------------------- |
| "怎么做"（有多种合理方案）   | Skill（`.qoder/skills`）                     |
| 项目方案选择与理由           | AGENTS.md / docs/ 的架构说明                 |
| 具体操作步骤、目录清单       | 对应 Skill 或 docs/                          |
| 一次性排查记录               | 记忆系统，不入库                             |

---

## 3. 写前检查（强制）

```
1. grep .qoder/rules/ 与 apps/*/.qoder/rules/ 是否有同主题已有规则
2. 检查 AGENTS.md 是否已有重叠约束
3. 判定：
   ├─ 重叠 > 50% → 更新已有规则，不新建
   ├─ 主题不同   → 可新建
   └─ 不确定     → 问用户
```

---

## 4. 文件格式

```yaml
---
name: xxx-rule            # 与文件名一致（不含 .md）
description: 一句话说清约束主题；按需加载的必须写清触发场景
alwaysApply: true         # true=常驻上下文，false=AI 按 description 判断加载
version: 1.0
owner: <真实姓名>          # 见 author-identity-rule
created: 2026-11-11
updated: 2026-11-11
last_verified: 2026-11-11
verified_against: <核对过的代码/配置依据>
---
```

| 策略     | `alwaysApply` | description 写法                                       |
| :------- | :------------ | :----------------------------------------------------- |
| 始终加载 | `true`        | 一句话点题即可（全文已注入，不参与判定）               |
| 按需加载 | `false`       | 必须写明适用场景与触发条件，是可判定的唯一依据         |

**命名**：`{主题}-rule.md`，全小写连字符，禁止领域前缀（作用范围靠目录区分）。

**常驻预算**：常驻规则合计控制在 400 行以内；超出时优先改按需加载。当前实测 6 条常驻共 380 行（2026-11-11），已接近上限——再加常驻前先降级或精简存量。

## 5. 推荐结构

```markdown
# 规则标题

> **适用范围**：…
> **加载方式**：始终 / 按需加载

## 核心规则
| # | 约束 |

## 禁令清单
| 禁止操作 | 原因 | 正确做法 |

## 自查清单（可选，按需加载类建议保留）
```

## 6. 编写要点

| 要点           | 反例                             | 正例                                     |
| :------------- | :------------------------------- | :--------------------------------------- |
| 结论唯一       | 尽量避免在事务里做远程调用       | 禁止在事务中执行远程调用                 |
| 禁令配正解     | 不要用 `dataIndex`               | 禁止 `dataIndex`，必须用 `field`         |
| 可验证         | 代码应该写得好                   | 颜色必须用 Arco Token，禁止硬编码色值    |
| 高信噪比       | 变量名用驼峰                     | 禁止执行 `prisma db push --force-reset`  |
| 有项目锚点     | 表格要用统一组件                 | 表格必须用 `<BasicTable>`（`src/components/basic-table`） |

---

## 7. 反模式

| 反模式                 | 表现                           | 正确做法                    |
| :--------------------- | :----------------------------- | :-------------------------- |
| Skill 写成 Rule        | 用禁令口吻描述有多种方案的事   | 拆成 Rule（约束）+ Skill    |
| 项目决策写成通用 Rule  | "本项目使用 MySQL"             | 放 AGENTS.md 或项目说明     |
| Rule 里写大段实现指导  | 禁令后紧跟实现步骤             | 约束留在 Rule，方法进 Skill |
| 过度细化               | 把每个操作步骤都约束           | 只约束关键边界              |
| 重复已有约束           | 两条规则各写一遍同一条禁令     | 定 SSOT，其他引用           |
| 常驻规则膨胀           | 什么都 `alwaysApply: true`     | 按触发频率分层              |

---

## 8. 写后自查

- [ ] name 与文件名一致，description 说清了主题与触发场景
- [ ] 每条约束都能一眼判定合规与否，无灰色地带
- [ ] 每条禁令都配了正确做法
- [ ] 与既有规则重叠 < 50%，没有重复禁令
- [ ] `owner` 是真实姓名，`updated` 是今天
- [ ] 常驻规则新增后总行数仍在预算内

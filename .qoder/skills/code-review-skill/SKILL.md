# 代码变更审查

> **职责**：判断"这次改动能不能合入"。事实判定，不做风格说教。
> **配套规则**：i18n、表格、页面骨架、图标、操作安全各自由对应 rule 约束；本技能只负责审查编排与证据。

---

## 0. 模式

| 模式 | 触发词                                     | 范围                                   |
| :--- | :----------------------------------------- | :------------------------------------- |
| 快速 | 快速过一下、简单看看、大概检查             | 只审本轮改动文件 + 直接调用方          |
| 深度 | 认真检查、详细评审、全面看看、默认（无关键词） | 五阶段全流程 + 关联配置 / i18n / 权限链路 |

两种模式都必须给出结论判定；差异在覆盖面，不在报告格式。

---

## 1. 证据原则

- 每条问题必须能落到 **文件 + 位置 + 实际行为**，禁止"这里可能有空指针"这类无证据结论
- 判断依据优先级：代码 > 配置 > 文档；文档与代码冲突时报告冲突，不要静默选一边
- 没看清的实现不评审，先读完整文件再结论
- 未验证项单独列出，不得混在"已通过"里

---

## 2. 阶段一：变更范围

1. 列出本轮所有改动文件（`git status` / `git diff --stat`），逐个读**完整文件**而非只看 diff 片段
2. 按类型分类并标注审查重点：

| 类型       | 本项目重点                                                                 |
| :--------- | :------------------------------------------------------------------------- |
| 新增页面   | 骨架五段结构、i18n 双份 locale、路由 / 菜单是否配套                         |
| 新增接口   | `@RequirePermission` 或 `@Public()`、DTO 校验、shared 类型、i18n 异常键      |
| shared 类型改动 | 后端是否已 `pnpm build`（shared dist 生效）、前端引用是否同步           |
| schema.prisma 改动 | 是否需要 `db:push` / `db:generate`、seed 是否受影响                  |
| 依赖变更   | 是否有重复依赖、版本与 Arco/Vite/Vue 主版本冲突                             |
| 配置变更   | `.env` / `settings.json` / `vite.config.*` 的多环境一致性、敏感信息         |

3. 规模评估：净变更 > 400 行时按模块拆分评审，报告里说明拆分方式，禁止千行 diff 一轮浅审

---

## 3. 阶段二：契约一致性（本项目最容易出错的一段）

| # | 检查项         | 判定标准                                                                 |
| :- | :------------- | :----------------------------------------------------------------------- |
| 1 | 类型三处一致   | `packages/shared/src/*.ts` 的类型 ↔ 后端 Service 返回 ↔ 前端 `api/*.ts` 使用处 完全对齐 |
| 2 | 响应格式       | Controller 直接返回业务数据；`{ code, message, data }` 由 `TransformInterceptor` 统一包装，禁止手工再包一层 |
| 3 | 异常消息       | Service / Guard 只抛 i18n key（如 `'auth.loginFailed'`）；`src/i18n/zh-CN/messages.json` 与 `en-US/messages.json` 必须同时存在该 key |
| 4 | 权限码三处一致 | `seed.ts` 的 `permission` ↔ Controller 的 `@RequirePermission` ↔ 前端 `v-permission` 字符串完全一致 |
| 5 | 菜单可打开     | `seed.ts` 的 `component`（如 `system/role/index`）↔ `views/**/index.vue` 实际路径一致 |
| 6 | 前端文案       | 模板 `$t()` / 脚本 `t()`，无硬编码中文；`locale/zh-CN.ts` 与 `en-US.ts` key 对应，且在 `src/locale/*.ts` 聚合导入 |
| 7 | 日期格式       | 后端日期字段用 `formatDate`，禁止 `.toISOString()` 输出 ISO 串 |
| 8 | 分页约定       | 返回 `{ list, total, page, pageSize }`；查询参数 `page` / `pageSize` |

---

## 4. 阶段三：代码逻辑

### 后端（apps/server）

| 类别       | 检查点                                                                     |
| :--------- | :------------------------------------------------------------------------- |
| 认证授权   | 新接口默认需认证；`@Public()` 仅用于登录/刷新/健康检查类；`super_admin` 绕过逻辑未被破坏 |
| 输入校验   | DTO 使用 class-validator 装饰器；service 内不做"信任前端"的边界假设         |
| 数据访问   | 查询是否缺 `where` / 分页缺 `take,skip`；循环内查询（N+1）；事务边界         |
| 密码与 token | bcryptjs 轮数 10；refreshToken 校验密钥用 `JWT_REFRESH_SECRET`，不复用 access 密钥 |
| 异常与日志 | 异常不吞掉；日志不输出密码、token、完整连接串                               |
| 时间与类型 | 空值 / `undefined` 参与计算；日期格式化统一                                 |

### 前端（apps/web）

| 类别       | 检查点                                                                     |
| :--------- | :------------------------------------------------------------------------- |
| 骨架与表格 | 页面五段结构；表格用 `BasicTable` + `field` / `slots.default`；固定列有 `width` |
| 状态与副作用 | `watch` 清理、`onUnmounted` 释放定时器/监听；弹窗关闭后重置表单           |
| 交互正确性 | loading 状态、重复提交、错误分支是否提示（Message）                         |
| 样式       | `<style scoped lang="less">`；颜色用 Arco Token；`:deep()` 而非 `/deep/`；弹窗样式挂载点合规 |
| 类型       | 无隐式 `any`；API 返回值有类型                                              |

### 通用

- 死代码、注释掉的实现、`console.log` 残留、TODO 无跟进人
- 空实现 / 兜底返回 `null` 而未标注（阶段四继续追）

---

## 5. 阶段四：全链路跑通

1. 从入口追到实现：前端 `api/xxx.ts` → 拦截器 baseURL → 后端 Controller → Service → Prisma
2. 确认没有 Mock、没有空方法、没有 `return []` 糊过去；确属"预留"的要在报告里标为豁免并说明依据
3. 动态路由链路：`menuFromServer: true` → `/api/auth/menus` → `transformMenusToRoutes` → `import.meta.glob` 能否匹配到新页面
4. 401 / 刷新链路：新接口是否会被拦截器误判（如 `@Public()` 接口不需要 token）

---

## 6. 阶段五：验证

| 变更类型         | 必须执行                                        |
| :--------------- | :---------------------------------------------- |
| 前端代码         | `pnpm build:web`（类型错误与构建错误才算通过）  |
| 后端代码         | `pnpm build:server`（tsc + nest 构建）          |
| shared 类型      | `pnpm build`（shared 先产出 dist）              |
| schema 改动      | `pnpm db:generate`，并说明是否已 `db:push`      |
| 中文文档 / 长文件 | `check-encoding.py` 抽查编码与行尾               |

行为级验证（点页面、看交互、看布局）由用户自行完成：报告里列出"需要人工验证的重点"，不要声称已验证。

---

## 7. 分级与结论

| 级别      | 含义                             | 示例                                                     |
| :-------- | :------------------------------- | :------------------------------------------------------- |
| P0-阻断   | 线上故障、数据损坏、安全漏洞     | 权限码不匹配导致 403 / 无限权限、密码明文落日志、无 `@Public` 的登录接口 |
| P1-严重   | 功能缺陷、契约不一致、性能退化   | shared 类型与后端不一致、i18n key 缺失导致报 key 原文、菜单点开空白 |
| P2-建议   | 可读性、一致性、轻微优化         | 命名、注释、骨架细节偏差                                 |
| P3-赞赏   | 值得推广的写法                   | 合理的防御性处理、清晰抽象                               |

结论：存在 P0 → **需返工**；仅 P1 → **有条件通过**；仅 P2/P3 → **通过**。
